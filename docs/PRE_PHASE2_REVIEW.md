Severity reflects potential impact; status distinguishes observed code behavior from conditional exploitation or unverified runtime risks. **No confirmed Critical or High unauthorized-spending vulnerability was found under the stated trusted-owner/deployer and correctly scoped agent-key assumptions.** No deployed key configuration exists to inspect.

## Controls that appear correct on inspection

- **Agent authority:** [model.rs:324](../src/model.rs#L324) checks zero deposit, exact mandate, direct agent/signer, approved key, recipient, amount, time and remaining budget. Approved key identity does not prove its protocol permission type: later provision the key on the **agent account**, receiver=vault, methods exactly `execute_payment`, finite explicit gas allowance. An approved agent full-access key would still pass contract policy but grant broader control of the agent account. Gas allowance is not the vault's token budget. [Official access keys](https://docs.near.org/protocol/accounts-contracts/access-keys).
- **Atomic limits:** [model.rs:358](../src/model.rs#L358) computes checked deltas, then records A/P/nonce before [contract.rs:116](../src/contract.rs#L116) constructs the promise. No asynchronous check/reserve gap was found. Other requests may intervene before settlement; network arrival order is not guaranteed. This matches [NEAR's debit-before-call rule](https://docs.near.org/smart-contracts/security/cross-contract-calls/reentrancy). Actual receipt rollback and competing submissions remain to be tested.
- **Callbacks/replay/refunds:** [contract.rs:126](../src/contract.rs#L126) combines private predecessor, one result and bounded native-transfer result reads. [model.rs:398](../src/model.rs#L398) settles only Pending, using stored amount, once. Expected transfer failure returns normally; it does not panic after a refund credit. [Official private callbacks](https://docs.near.org/smart-contracts/security/cross-contract-calls/callbacks), [failure-path handling](https://docs.near.org/smart-contracts/security/cross-contract-calls/callback-panics). There is correctly no agent refund: the agent attached zero principal, and returned value belongs to the vault. [Official refunds](https://docs.near.org/smart-contracts/security/cross-contract-calls/refunds).
- **Owner/revocation:** [model.rs:170](../src/model.rs#L170) restricts initialization to the direct parent and intended caller; [model.rs:336](../src/model.rs#L336) blocks revoked/expired requests while settlement deliberately ignores those later flags. Neither flag recalls a scheduled transfer. [NEAR asynchronous execution](https://docs.near.org/smart-contracts/anatomy/crosscontract).

## Missing tests and integration prerequisites

No tests, builds, accounts or node processes were started in this review. These are gates for the **next authorized phase**:

1. **Harness topology:** create the intended owner and a direct child vault; a generic independent `dev_deploy` account plus an unrelated owner will fail [model.rs:173](../src/model.rs#L173). Establish reserve before explicit principal funding; owner-admin calls currently attach zero. Keep trusted fixture keys off the agent wrapper.
2. **Compiled-Wasm authorization:** reinitialization, malformed U128/U64/key input, attached-deposit rejection, restricted key wrong receiver/method/transfer/add-key/deploy attempts, direct full-access/proxy attacks, real private-callback forgery, and R2's owner-held function-call-key case.
3. **Real native outcomes:** transfer success and failure to an absent **named** account, callback storage/events, no agent refund, refund arrival and final balance reconciliation. A plain transfer does not invoke a recipient contract's panicking method. [Official native transfers](https://docs.near.org/smart-contracts/anatomy/actions).
4. **Gas/fault/solvency:** maximum state/recipient/key sizes; success/failure callback gas; low parent gas with atomic rollback; callback failure retaining P; refund lag and reserve boundaries. Use separately labeled fault instrumentation where receipt timing cannot be controlled.
5. **Concurrency/replay:** barrier-release three independent-key .40 requests against fresh B=1.00; verify all three executor receipts, two acceptances/one budget rejection, genuine pending overlap, replay during/after settlement, duplicate settlement and revoke ordering. Protocol nonce rejection is not budget-enforcement evidence. Inspect all descendants and wait for refunds/finality, rather than root status alone. [Official transaction lifecycle](https://docs.near.org/protocol/transactions/transaction-execution).

**SDK/platform:** [Cargo.toml:5](../Cargo.toml:5) and [Cargo.toml:16](../Cargo.toml:16) match the [tagged SDK 5.29.1 Rust 1.93 requirement](https://raw.githubusercontent.com/near/near-sdk-rs/near-sdk-v5.29.1/Cargo.toml). Existing Wasm evidence reports protocol minimum 84. No new incompatibility is confirmed. The proposed [near-workspaces 0.23.0 manifest](https://raw.githubusercontent.com/near/near-workspaces-rs/near-workspaces-v0.23.0/workspaces/Cargo.toml) uses the nearcore 2.13 family/near-sandbox 0.3.12; pin actual resolution and runtime version. The [framework requirements](https://raw.githubusercontent.com/near/near-workspaces-rs/main/README.md) list Linux/macOS sandbox support. Windows compilation alone is insufficient. Current [integration docs](https://docs.near.org/smart-contracts/testing/integration-test) show a direct `near-sandbox` API; do not assume those examples match the older workspaces API. A separate Linux runner/host and test crate are still unprovisioned. Linux ABI generation can wait; sandbox can load the existing no-ABI Wasm.

## Decision and required fixes

**GO for Phase 2A, only after explicit approval, using ephemeral synthetic sandbox balances.** No mandatory code patch before that experiment was established by this review. Required setup corrections are the owner/child-vault topology, correctly scoped agent keys, adequate reserve funding and a working Linux sandbox harness. Measurement and adversarial tests are the purpose of that phase, not preexisting evidence.

R2 hardening may wait while the sandbox owner has no delegated administrative key. R1 key removal, R4 recovery/withdrawal and R8 publication can wait under the disposable-fixture assumptions; do not silently extend those assumptions to real custody. Callback-gas, physical solvency and runtime authorization/concurrency validation must pass before a successful integration claim. **NO-GO for real-value funding or deployment on the strength of this review alone.**
